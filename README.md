# 接水 · 极简饮水机助手

> 把「胖乖生活」里接一杯水这件事，做成**打开、扫码、接水、走人**。

官方 App 里全是广告、弹窗、首页推荐，而实际每天要用的只有一件事：扫一下饮水机上的二维码，接杯水。
这个项目把那一条链路单独拆出来，做成两个形态 —— **一个 285 KB 的安卓 APK**，和**一个不用安装的网页**。

---

| --- | --- | --- |

> 安卓用户想要更顺手的扫码体验（原生相机对焦更快）再装 APK。

## ✨ 它做了什么

- **打开就是扫码** —— 没有首页推荐、没有开屏广告、没有弹窗，进来就是相机
- **扫码即开阀，手机上不用再点一次「开始接水」** —— 扫完机器立刻认到你，直接在机器上按「开始」就出水，和官方 App 一个节奏
- **只认饮水机** —— 扫到别的业务（淋浴、洗衣等）直接提示，不会误操作
- **只走支付宝免密** —— 不弹收银台、不跳转、不输密码，接完自动结算
- **水卡 / 小票 / 积分照常生效** —— 见下一节
- **结算明细如实给** —— 用水量、原价、小票抵扣、积分抵扣、实付，一屏看完（图 4）
- **连续接水不用重开 App** —— 接完热水按返回，回首页直接扫凉水那台
- **手动输入兜底** —— 相机权限给不了、镜头脏了、二维码磨损了，可以直接输设备号

## 💳 「我之前买的水卡还能用吗？」

**能，而且不需要任何迁移动作。**

水卡余额、小票、积分、支付宝免密签约，全部存在胖乖生活的**服务器上**，并与**你的账号**绑定。
客户端只是个遥控器 —— 换一个客户端登录同一个账号，服务端照旧扣它的水卡、走它的免密协议。

这不是"我猜的"，是从官方代码里读出来的：`StartStatusAct.initData()` 里 `payType` 是硬编码的
`String.valueOf(PayTypeEnum.ALIPAY_NOT_PASSWORD.getType())`（= `"15"`，支付宝免密），
客户端从未参与"用哪张卡"的决策 —— 那是服务端按账号算的。

所以本项目要做的只是：**带上你的 token，把 `skuId` 和 `payType=15` 发给服务端**。

<details>
<summary>顺带一提：这里踩过一个很贵的坑</summary>

`PayTypeEnum` 的构造签名是 `(name, ordinal, type, str)`，服务端要的是 **`type`** 不是 `ordinal`。
`ALIPAY` = type `13`、`ALIPAY_NOT_PASSWORD` = type `15`、`WALLET` = type `2`。

早期误传 `1`（那是 ordinal）的后果很隐蔽：水票**照扣不误**（支付宝侧显示「通用小票」），
但订单在胖乖侧一直挂着「待支付」，而这张幽灵单还会**挡住你下一次接水**。
表面症状是"接水没反应"，实际是上一单没结清。

</details>

## 🚀 开始使用

### 网页版（最快）

1. 手机浏览器打开 **<https://jieshui.pages.dev>**
2. 登录 —— 手机号 + 短信验证码，或直接粘贴 token
3. 扫饮水机上的二维码，机器上按「开始」

> 想当 App 用：浏览器菜单里选「添加到主屏幕」，之后从桌面图标打开，全屏无地址栏。

### 安卓 APK

1. 到 [Releases](../../releases/latest) 下载 `jieshui.apk`
2. 安装（首次需要允许「安装未知来源应用」）
3. 登录方式和网页版相同

### token 从哪来

客服端登录后会自己保存 token，一般不用你操心。如果短信验证码当天次数用完了，
或者服务端返回 `forcedBind`（老账号要求先绑微信/支付宝），可以从官方 App 里直接读：

```bash
bash tools/token_from_mmkv.sh      # 连着 adb，从官方 App 的 MMKV 里读 token
```

也可以在任一端的 **设置 → 查看并复制完整 Token**，把登录态搬到另一台设备。

拿到 token 后，想先确认它能不能用、水卡还剩多少：

```bash
python tools/probe_chain.py <token>
```

只调只读接口（查登录态、余额、最近用的设备、设备详情、水卡额度、免密签约状态），
**不会开水、不会下单、不会扣钱**。

## 🔍 几个刻意做对的细节

做这个东西的过程中，有一半时间花在"看起来没问题但实际会坑人"的地方：

**扫码距离** —— 一开始整幅压到 480 解，二维码在画面里占 18% 就认不出了，表现出来就是"稍微拿远点就扫不上"。
现在主路径是把取景框对应的那块**原生像素**切出来解（上限 1080），整幅 720 只作兜底、每 3 帧跑一次。
取景窗也不再是"整屏铺满再 `cover`"——那样竖屏时横向只剩中间 26%（等效放大 3.85 倍），
用户会以为"相机自己放大了"然后往后退，越退越扫不到。现在是正方形取景窗，**框里看到的就是解的那块像素**。

APK 侧还额外做对了两件事：**不再每帧旋转整幅**（QR 的定位图形本来就旋转无关，ZXing 会自己算仿射变换，
旧实现每帧白花 2.3ms + 2MB），以及**预览分辨率按"取景框里能拿到多少原生像素"挑**而不是按短边——
预览按比例铺满屏幕，**比例越窄放大得越狠**，同一块框落到的像素反而更少。1080x2400 的屏上，
1440x1080 要放大 1.67 倍（框内 440px），1920x1080 只放大 1.25 倍（框内 587px），
两者短边都是 1080，按短边挑就会挑到前者，白白少 33% 解析力。

**不给用户看假数据** —— `goods/water/sync` 返回的 `amount` 不是金额（接 0.2L 时它返回 `76`，
真实原价是 ¥0.04），官方从不展示它。水量和金额一律以 `order/detail` 为准。

**结算结果如实说** —— 建单失败就写「订单没有生成成功」且不显示订单号；
扣款没确认就写「支付还没确认」并提醒去清掉「待支付」单。
early 版本两种情况都写"已结算"，用户下次被幽灵单挡住时完全不知道为什么。

**断网不会永远转圈** —— 等待期连续失败 5 次就明确退出；以前 `catch` 里的 `continue`
跳过了等待计数，断网时会一直停在「请在机器上按开始」。

**不会停错机器** —— 等待期又扫了另一台，旧的那一轮会被立即作废，并且只停**它自己那台**的水。

**接水前先登记后付费渠道** —— 少调一个 `payChannelRoute/addUserAfterPayChannel`，
支付宝侧就会按「通用小票」结算而不是账号已签约的「企鹅共享小额免密支付」，
订单也不会推进到已支付。

<details>
<summary>还有一堆关于扫码灵敏度的实测数据（点开看）</summary>

同一张二维码按不同比例缩进画面，比较各种解码策略：

| 二维码占画面高度 | 旧的整幅 480 | 整幅 720 | 取景窗原生像素 |
| --- | --- | --- | --- |
| 18% | ✗ | ✓ | ✓ |
| 14% | ✗ | ✓ | ✓ |
| 12% | ✗ | ✗ | ✓ |
| 8% | ✗ | ✗ | ✓ |

APK 侧（Camera1 + ZXing）用 `tools/ScanCoreTest.java` 在 JVM 里直接跑**生产代码** `ScanCore.decode` 量出来的：

| 二维码占取景框 | 1280x720（框内 391px） | 1440x1080（440px） | 1920x1080（587px） | 2048x1536（760px） |
| --- | --- | --- | --- | --- |
| 16% | ✓ | ✓ | ✓ | ✓ |
| 12% | ✓ | ✓ | ✓ | ✓ |
| 11% | ✗ | ✓ | ✓ | ✓ |
| 10% | ✗ | ✗ | ✓ | ✓ |
| 9% | ✗ | ✗ | ✓ | ✗ |
| 8% | ✗ | ✗ | ✓ | ✓ |

「能认出的最小占比」：1280x720 → **12%**，1440x1080 → **11%**，1920x1080 → **8%**，2048x1536 → **6%**。
旧规则会挑 1440x1080，新规则挑 1920x1080 —— 距离余量从 11% 提到 8%，**大约多出 40% 的可用距离**。

（表里 9% 那一行有 ✗ 是采样抖动：固定几个位置试出来的边界值会差一档，真实使用中手会动，所以按"最好的那一次"统计。）

其他几条：

- 不预旋转整幅也能解：0 / 90 / 180 / 270 度全过（靠 ZXing 自己算仿射变换）
- 只解取景框那块方块：每帧 `2.7ms → 1.2ms`
- 整幅兜底如果每帧都跑，无码帧反而 `3.2ms → 4.5ms`（**慢 41%**）；改成每 8 帧跑一次后降到 `1.7ms`（比原来快 1.9 倍）
- 每帧省下的「旋转 + 复制整帧」是 `2.3 + 0.2 = 2.5ms`，而只裁框只要 `0.04ms`
- 码比取景框还大时，靠每 8 帧一次的兜底也能在 0.3 秒内捞回来

教训：**优化时不能拿"顺利路径"的耗时当平均耗时 —— 顺利路径恰恰是少数。**

</details>

## 🛠 自己构建

<details>
<summary>展开：构建 APK / 部署网页 / 跑回归</summary>

### APK

不需要 Gradle，`build.sh` 直接用 aapt2 + javac + d8 + apksigner：

```bash
bash build.sh        # → apk/jieshui.apk
```

需要自备（都不在仓库里）：JDK 17、Android SDK build-tools 34 + platforms/android-34、
`zxing-core-3.5.x.jar`。签名用 `build/jieshui.keystore`，密码走环境变量 `KS_PASS` / `KS_KEY_PASS`。

mock 版（只跑 UI，不联网）：

```bash
python tools/make_test.py && bash build_test.sh   # → apk/jieshui-test.apk
```

> `android_test/` 是 `tools/make_test.py` 生成的，**不要手改**，否则会跟真源码漂移。

### 网页版

```bash
python -m http.server 8899 --directory web    # 本地调试（必须 localhost 或 HTTPS，否则拿不到摄像头）
bash tools/deploy.sh                          # 发到 Cloudflare Pages
```

> ⚠️ 网页版**必须跑在 HTTPS 或 localhost** 上，浏览器不会在 http 页面授予摄像头权限。

### 回归

```bash
CDP_PORT=9501 node tools/cdp.js flow "http://127.0.0.1:8899/index.html" tools/flow_auto.js 390 844 900
```

`tools/flow_*.js` 是一堆针对具体 bug 的回归脚本，每个都能独立跑，看文件头注释就知道在测什么。
`tools/cdp.js` 是个 200 行的极简 CDP 客户端，不需要 puppeteer。

> 真实链路回归（`flow_real.js` / `flow_token_live.js`）需要 `QK_TOKEN` 环境变量，
> 仓库里不含任何 token。

</details>
