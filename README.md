# 接水 · 极简饮水机助手

> 把「胖乖生活」里接一杯水这件事，做成**打开、扫码、接水、走人**。

官方 App 里全是广告、弹窗、首页推荐，而实际每天要用的只有一件事：扫一下饮水机上的二维码，接杯水。
这个项目把那一条链路单独拆出来，做成两个形态 —— **一个 285 KB 的安卓 APK**，和**一个不用安装的网页**。

---

## 📱 两种形态，任选其一

| | 安卓 APK | 网页版 PWA |
| --- | --- | --- |
| **怎么用** | 下载安装包 | **打开链接就能用，无需安装** |
| **地址** | [Releases](../../releases/latest) 里的 `jieshui.apk` | **<https://jieshui.pages.dev>** |
| 体积 | 285 KB | 首次加载约 200 KB，之后走缓存 |
| 扫码 | 原生相机 + ZXing | 浏览器摄像头 + jsQR / 原生 BarcodeDetector |
| 离线 | 完全本地，除接口外不联网 | 装到主屏幕后可离线打开界面 |

> 🌐 **网页版无需安装、无需下载，手机浏览器直接打开 <https://jieshui.pages.dev> 即可。**
> 安卓用户想要更顺手的扫码体验（原生相机对焦更快）再装 APK。

## ✨ 它做了什么

- **打开就是扫码** —— 没有首页推荐、没有开屏广告、没有弹窗，进来就是相机
- **扫码即开阀，手机上不用再点一次「开始接水」** —— 扫完机器立刻认到你，直接在机器上按「开始」就出水，和官方 App 一个节奏
- **只认饮水机** —— 扫到别的业务（淋浴、洗衣等）直接提示，不会误操作
- **只走支付宝免密** —— 不弹收银台、不跳转、不输密码，接完自动结算
- **水卡 / 小票 / 积分照常生效** —— 见下一节
- **首页就能看到还剩多少小票** —— 右上角一个绿色徽标，不用回官方 App 翻账户
- **登录页就能选「记住登录」** —— 默认勾选，公用设备取消勾选即可，设置里也同步
- **结算明细如实给** —— 用水量、原价、小票抵扣、积分抵扣、实付，一屏看完（图 4）
- **没接水就不产生订单** —— 扫码后没出水直接在机器上按「结算」，只会告诉你"本次没有出水，未产生费用"，不会弹一张订单号是 null 的结算页
- **连续接水不用重开 App** —— 接完热水按返回，回首页直接扫凉水那台
- **手动输入兜底** —— 相机权限给不了、镜头脏了、二维码磨损了，可以直接输设备号

## 💳 「我之前买的水卡还能用吗？」

**能，而且不需要任何迁移动作。**

水卡余额、小票、积分、支付宝免密签约，全部存在胖乖生活的**服务器上**，并与**你的账号**绑定。
客户端只是个遥控器 —— 换一个客户端登录同一个账号，服务端照旧扣它的水卡、走它的免密协议。

这不是"我猜的"，是从官方代码里读出来的：`StartStatusAct.initData()` 里 `payType` 是硬编码的
`String.valueOf(PayTypeEnum.ALIPAY_NOT_PASSWORD.getType())`（= `"15"`，支付宝免密），
客户端从未参与"用哪张卡"的决策 —— 那是服务端按账号算的。

所以本项目要做的只是：**带上你的 token，把 `skuId` 和 `payType=15` 发给服务端**。

<details>
<summary>顺带一提：这里踩过一个很贵的坑</summary>

`PayTypeEnum` 的构造签名是 `(name, ordinal, type, str)`，服务端要的是 **`type`** 不是 `ordinal`。
`ALIPAY` = type `13`、`ALIPAY_NOT_PASSWORD` = type `15`、`WALLET` = type `2`。

早期误传 `1`（那是 ordinal）的后果很隐蔽：水票**照扣不误**（支付宝侧显示「通用小票」），
但订单在胖乖侧一直挂着「待支付」，而这张幽灵单还会**挡住你下一次接水**。
表面症状是"接水没反应"，实际是上一单没结清。

</details>

## 🚀 开始使用

### 网页版（最快）

1. 手机浏览器打开 **<https://jieshui.pages.dev>**
2. 登录 —— 手机号 + 短信验证码，或直接粘贴 token
3. 扫饮水机上的二维码，机器上按「开始」

> 想当 App 用：浏览器菜单里选「添加到主屏幕」，之后从桌面图标打开，全屏无地址栏。

### 安卓 APK

1. 到 [Releases](../../releases/latest) 下载 `jieshui.apk`
2. 安装（首次需要允许「安装未知来源应用」）
3. 登录方式和网页版相同

### token 从哪来

客服端登录后会自己保存 token，一般不用你操心。如果短信验证码当天次数用完了，
或者服务端返回 `forcedBind`（老账号要求先绑微信/支付宝），可以从官方 App 里直接读：

```bash
bash tools/token_from_mmkv.sh      # 连着 adb，从官方 App 的 MMKV 里读 token
```

也可以在任一端的 **设置 → 查看并复制完整 Token**，把登录态搬到另一台设备。

拿到 token 后，想先确认它能不能用、水卡还剩多少：

```bash
python tools/probe_chain.py <token>
```

只调只读接口（查登录态、余额、最近用的设备、设备详情、水卡额度、免密签约状态），
**不会开水、不会下单、不会扣钱**。

## 🔍 几个刻意做对的细节

做这个东西的过程中，有一半时间花在"看起来没问题但实际会坑人"的地方：

**取景就是画面本身** —— 预览按原始比例**整幅显示**（`object-fit:contain` / 安卓端 contain 布局），
一像素都不裁、不放大。取景框只是画在画面中央的一圈准星，**屏幕上看得见的，就是能被识别的**。
这条是踩了三次坑才定下来的：

1. 全屏 `cover` + 整幅压到 480 解 —— 竖屏里 cover 把画面横向裁掉 74%、等效放大 3.85 倍，
   用户以为离得太近就往后退，越退码越小，反而更扫不上；
2. 把预览缩成一个小方块只显示框内 —— 不裁了，但框外全黑，看着像相机坏了；
3. contain + 一个固定尺寸的方框 —— 画面只占中间一条细带时，框比画面还高，
   上下落在黑边上，用户照框去对，码其实早就出画面了。

**解码整幅，不裁块** —— 既然画面整幅可见，解码也必须整幅。
只解中间那一块等于把画面四角看得见的码主动丢掉，表现就是"明明在画面里，怎么对都对不上"。
实测把码贴在右上角：整幅解 **认得出**，只裁中心块 **认不出**（`tools/ScanCoreTest.java` 第 6 组）。

**扫不出来就拍张全分辨率照片** —— 预览流的分辨率是有天花板的（多数手机网页给到 1920x1440 就到顶），
码占画面 8% 时在预览里只剩 86px，25 个模块摊下来 3.5px/模块，已经非常勉强。
所以两端都做了同一件事：连续预览扫两三秒没结果，**拍一张全分辨率静态照片**再识别。
照片能到 4000x3000，比预览多一个数量级的像素，识别距离是预览的好几倍。

**反色码（深底亮模块、反光贴纸）** —— 先用正常极性解，解不出再把像素逐字节取反重解一遍。
网页端这里还有个隐蔽的坑：jsQR 的 `inversionAttempts:'onlyInvert'` 会直接抛
`Cannot read properties of undefined (reading 'height')` ——
因为它的 `inverted` 矩阵只在 `attemptBoth` / `invertFirst` 时才产出，用 `onlyInvert` 拿到的是 `undefined`。
这个异常被外层 catch 吞了，所以上一版的"反色兜底"其实**从未生效过**。改成 `invertFirst` 才真正跑起来。

**APK 侧另外几件**：**不再每帧旋转整幅**（QR 的定位图形本来就旋转无关，ZXing 会自己算仿射变换，
旧实现每帧白花 2.3ms + 2MB）；**预览尺寸按整幅像素挑**（现在是解整幅，能扫多远取决于整幅有多少像素，
1920x1080 比 1440x1080 多 78%）；**对焦三段兜底并把对焦区域钉在画面中央**（连续图像 → 连续视频 → 自动，
有些机器没有前两者就退定焦，凑近拍必糊；不少国产 ROM 默认把对焦区域均摊到整个画面，钉在中心后合焦快得多）；
**数码变焦归位**（上一次用完留了个非 1 的变焦，表现就是"相机自己放大了"）；
**扫码震动**（手抖时眼睛未必看屏幕，触感是"成了"最直接的反馈，两端一致）。

**APK 侧两个"画面正常但就是不认"的坑**（都已修，都是不报错、纯靠推理找出来的）：

- `camera.takePicture()` 原来是在相机派发预览帧的那条线程上调的。那条线程正在把帧交给我们，
  在上面调拍照会阻塞等它自己把帧交完 —— 轻则卡几秒，重则在部分 ROM 上直接不再回调。
  网页端的 `ImageCapture` 走的是独立通道，所以同样的逻辑在浏览器里一直没事，
  **这正是"网页能扫、App 扫不出"的一部分来源**。
- 预览尺寸原来读的是**我们请求的那一份**（`pr.getPreviewSize()`），而不是相机实际采用的。
  有些 ROM 会静默换掉档位，这时给 `addCallbackBuffer` 的缓冲偏大或偏小，相机侧直接不回调 ——
  症状是画面一切正常，但一帧都不进识别，而且完全没有报错。现在改成回读
  `camera.getParameters().getPreviewSize()`，取景框也按真实尺寸排布。
- 拍完照之后必须**先把回调缓冲重新交回去再 `startPreview()`**。只调 `startPreview()`
  画面会回来，但相机手上一个缓冲都没有，`onPreviewFrame` 再也不触发 ——
  表现是"拍了一张没认出来，之后就彻底不动了"。

**不给用户看假数据** —— `goods/water/sync` 返回的 `amount` 不是金额（接 0.2L 时它返回 `76`，
真实原价是 ¥0.04），官方从不展示它。水量和金额一律以 `order/detail` 为准。

**结算结果如实说** —— 建单失败就写「订单没有生成成功」且不显示订单号；
扣款没确认就写「支付还没确认」并提醒去清掉「待支付」单。
早期版本两种情况都写"已结算"，用户下次被幽灵单挡住时完全不知道为什么。

**判断"付没付"看订单状态，不看 `order/sync` 的返回值** —— 接水一两秒就结算时，
那几次 `order/sync` 很可能全部落空，但支付宝的异步扣款其实已经成功了。
官方 H5 包里的状态表是 `0 待支付 / 1 已失效 / 2 使用中或已完成 / 3 已完成 / 4 退款中 / 5 已退款`，
只有 2 和 3 才算钱已结清。所以两端都改成：`order/sync` 走完之后再拉一次 `order/detail` 看
`orderStatus`，还不确定就再等两轮。用户实测过这个场景 —— 旧版写「支付还没确认」，
他被引导去官方 App 点「立即支付」，点开发现根本没有待支付订单。

**断网不会永远转圈** —— 等待期连续失败 5 次就明确退出；以前 `catch` 里的 `continue`
跳过了等待计数，断网时会一直停在「请在机器上按开始」。

**不会停错机器** —— 等待期又扫了另一台，旧的那一轮会被立即作废，并且只停**它自己那台**的水。

**接水前先登记后付费渠道** —— 少调一个 `payChannelRoute/addUserAfterPayChannel`，
支付宝侧就会按「通用小票」结算而不是账号已签约的「企鹅共享小额免密支付」，
订单也不会推进到已支付。

<summary>还有一堆关于扫码灵敏度的实测数据（点开看）</summary>

同一张二维码按不同比例缩进画面，比较各种解码策略：

| 二维码占画面高度 | 旧的整幅 480 | 整幅 720 | 取景窗原生像素 |
| --- | --- | --- | --- |
| 18% | ✗ | ✓ | ✓ |
| 14% | ✗ | ✓ | ✓ |
| 12% | ✗ | ✗ | ✓ |
| 8% | ✗ | ✗ | ✓ |

APK 侧（Camera1 + ZXing）用 `tools/ScanCoreTest.java` 在 JVM 里直接跑**生产代码** `ScanCore.decodeWhole` 量出来的：

| 二维码占画面 | 1280x720 | 1440x1080 | 1920x1080 | 2048x1536 |
| --- | --- | --- | --- | --- |
| 16% | ✓ | ✓ | ✓ | ✓ |
| 12% | ✓ | ✓ | ✓ | ✓ |
| 11% | ✗ | ✓ | ✓ | ✓ |
| 10% | ✗ | ✗ | ✓ | ✓ |
| 9% | ✗ | ✗ | ✓ | ✗ |
| 8% | ✗ | ✗ | ✓ | ✓ |
| 7% | ✗ | ✗ | ✗ | ✓ |
| 6% | ✗ | ✗ | ✗ | ✓ |

「能认出的最小占比」：1280x720 → **12%**，1440x1080 → **11%**，1920x1080 → **8%**，2048x1536 → **6%**。
旧规则会挑 1440x1080，新规则挑 1920x1080 —— 距离余量从 11% 提到 8%，**大约多出 37% 的可用距离**。
（表里个别 ✗ 是采样抖动：固定几个位置试出来的边界值会差一档，真实使用中手会动，所以按"最好的那一次"统计。）

而**拍照兜底**又把这条线整体往外推了一大截：预览 1920x1080 时码占 8% 勉强能认，
同一个距离下拍出来的 4000x3000 照片里，码有 240px、25 个模块摊到 9.6px/模块，非常稳。

其他几条：

- 不预旋转整幅也能解：0 / 90 / 180 / 270 度全过（靠 ZXing 自己算仿射变换）
- 整幅解每帧 `4ms`（1920x1080），裁块解 `1.2ms` —— 多花 2.8ms 换来"看得见就认得出"
- 每帧省下的「旋转 + 复制整帧」是 `2.3 + 0.2 = 2.5ms`，而只裁框只要 `0.04ms`
- 码贴在画面四角：整幅解 ✓，只裁中心块 ✗

教训：**优化时不能拿"顺利路径"的耗时当平均耗时 —— 顺利路径恰恰是少数。**
</details>

## 🛠 自己构建

<details>
<summary>展开：构建 APK / 部署网页 / 跑回归</summary>

### APK

不需要 Gradle，`build.sh` 直接用 aapt2 + javac + d8 + apksigner：

```bash
bash build.sh        # → apk/jieshui.apk
```

需要自备（都不在仓库里）：JDK 17、Android SDK build-tools 34 + platforms/android-34、
`zxing-core-3.5.x.jar`。签名用 `build/jieshui.keystore`，密码走环境变量 `KS_PASS` / `KS_KEY_PASS`。

mock 版（只跑 UI，不联网）：

```bash
python tools/make_test.py && bash build_test.sh   # → apk/jieshui-test.apk
```

> `android_test/` 是 `tools/make_test.py` 生成的，**不要手改**，否则会跟真源码漂移。

### 网页版

```bash
python -m http.server 8899 --directory web    # 本地调试（必须 localhost 或 HTTPS，否则拿不到摄像头）
bash tools/deploy.sh                          # 发到 Cloudflare Pages
```

> ⚠️ 网页版**必须跑在 HTTPS 或 localhost** 上，浏览器不会在 http 页面授予摄像头权限。

### 回归

```bash
CDP_PORT=9501 node tools/cdp.js flow "http://127.0.0.1:8899/index.html" tools/flow_auto.js 390 844 900
```

`tools/flow_*.js` 是一堆针对具体 bug 的回归脚本，每个都能独立跑，看文件头注释就知道在测什么。
`tools/cdp.js` 是个 200 行的极简 CDP 客户端，不需要 puppeteer。

> 真实链路回归（`flow_real.js` / `flow_token_live.js`）需要 `QK_TOKEN` 环境变量，
> 仓库里不含任何 token。

</details>
