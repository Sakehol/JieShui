## 接水 v1.0.9 · 「接水中」现在只在真的出水后才出现

上一版（v1.0.8）我以为已经修好了，其实只修了一半 —— 你复测发现「已就绪」只维持 1 秒就跳「接水中」。这次找到了真正的判据。

### 我错在哪

判断「水有没有出来」，我先后试了两个都不对的信号：

**第一个：`workStatus === 2`**
机器屏幕上写着「设备已解锁 (6)秒 / 轻触【开始】键出水」，这个状态下 `workStatus` 就是 2。
用户不按开始，它一直是 2。所以 2 的含义是「机器认得你了、阀门待命」，不是「水在流」。

**第二个：`identify` 有值**
这是 v1.0.8 换上的判据，也正是你说「只维持 1 秒」的原因 ——
`identify` 是**解锁后服务端立刻就给的「建单凭据」**，扫码瞬间就有值。
拿它当出水信号，等于第一次轮询（约 1.2 秒）就断定「水出来了」。

### 这次用的判据

`sync.amount` 相对**解锁那一刻的基线**有没有增长。

`amount` 不是金额（单位很怪，接 0.2L 时它是 `76`），但官方正是拿它判断「这一单有没有消费」。
关键是它在**待命时是个固定值**（多数机器是 0，也有的不是），只有真正出水之后才开始变大。

所以现在的逻辑是：

1. 第一次 sync 时，把 `amount` 记成基线 `baseAmount`
2. 之后每次 sync，只有 `amount > baseAmount` 才算「水出来了」
3. 一旦出水，就切「接水中」并开始计时

这样无论 `amount` 的待命值是不是 0，都判断得对。

### 顺带修好的两处

**机器的「暂停」不再误判成结算**
以前出水后只要 `workStatus` 离开 RUNNING 就去结算 —— 但按「暂停」也会离开。
现在要连续两次 `amount` 都不再增长，才算真的结束。

**扫码后一滴水没接的文案统一了**
你说得对：既然「已就绪」状态下点取消和机器上按结算，结果都是「没接水、没花钱」，
那文案就不该分两套。现在统一显示：

> **已取消**
> 本次没有接水，未产生费用

（以前「机器上结算」会显示成「已结算 / 机器上已结算，本次没有出水，未产生费用」，
另一条路显示「没有在机器上按开始，本次未接水」—— 两套说法容易让人以为出了两回事。）

### 测试这次为什么能拦住

mock 也一起改了：等待期现在给的是 `workStatus: 2` + `identify: 'IDENTIFY_A'` + `amount: '0'`
—— 和真机一模一样（identify 有值、amount 为 0）。用旧代码跑这个 mock，
「已就绪」一秒就跳「接水中」，测试立刻失败。改完之后才通过。

之前测试一直绿，是因为 mock 里 `identify` 是空的 —— 又一次「mock 比真机宽松」。

### 验证

- `flow_auto`：扫码后 4 秒仍是「已就绪 / 请在机器上按「开始」」，`settleCallsWhileWaiting: 0`；
  按下开始后才切「接水中 / 水已开，正在计量」
- `flow_settle_empty`：解锁后没出水直接结算 → 「已取消 / 本次没有接水，未产生费用」，
  `settleCalls: 0`、`hasNull: false`
- APK 模拟器：进设备页后「已就绪」稳定保持（截图对比 2 秒 / 5 秒两帧都是「已就绪」），
  出水后才跳「接水中」，结算页六行明细正常
