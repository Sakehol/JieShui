## 接水 v1.0.5 · 点阵二维码终于能扫了

这一版解决的是那个反复出现的问题：**饮水机屏幕上的码明明清清楚楚，App 就是扫不出来。**

### 找到了：不是「糊」，是「不连通」

你截图里那种蓝色二维码，每个模块是一个**分离的圆点**，点与点之间留着亮缝。
人眼一看就是一张正常的码，但 ZXing 和 jsQR 的定位流程都会失败 ——
因为二维码三个定位图形（那三个大方块）靠的是 `1:1:3:1:1` 的**扫线宽度比例**，
亮缝把这段比例切碎了，扫描线走过去数出来的不是 1:1:3:1:1，于是连角都找不到。
找不到角，纠错等级再高也没用。

**所以之前所有方向都是错的，而且都实测验证过了：**

| 试过的办法 | 结果 |
| --- | --- |
| 换二值化器（全局直方图 / 混合） | 全部解不出 |
| 提高分辨率（720 → 1080 → 1536） | 解不出 |
| 降低分辨率 / 半尺寸再解 | 解不出 |
| 锐化（unsharp） | 解不出 |
| 形态学膨胀（半径 1~4） | 解不出 |
| 反色 | 解不出 |
| **闭运算（先腐蚀后膨胀，填缝）** | **解得出** ✓ |

原理很直接：闭运算会先把比「缝」宽的暗区向外扩张、再收缩回来，
**把亮缝填上，让分离的码点重新连成实心方块**，定位图形的比例就恢复了。

### 双端同步

- **安卓**：`ScanCore.decodeWhole` 现在走四遍 —— 整幅原分辨率 → 缩一半 → **点阵码专修（960 宽 + 闭运算 r=2/r=3）** → 整幅反色。
  点阵码那条通道每 4 帧跑一次（约 0.4 秒一轮），不是每帧都做，避免正常扫码掉帧。
- **网页版**：`app.js` 里加了同一套可分离闭运算，预览画面隔帧跑、拍照兜底那张图从 r=1 到 4 全试。

闭运算写成「先横一遍再竖一遍」的可分离形式，复杂度 O(n·r) 而不是 O(n·r²)，
960 宽上只要 5~9 ms —— 这就是它能塞进实时预览里的原因。

### 顺带：失败样张会存下来

如果还是扫不出来，App 会把那张没认出来的原始照片存到相册
`Pictures/接水扫码样张/`（只保留最近 3 张，不申请额外权限）。
把图发回来我就能直接用真图定位，不用再猜。

### 实测

网页端代码跑在同一批合成图上（`build/webtest_dot.js`，直接用 `web/app.js` 里的滤波函数 + jsQR）：

```
raw jsQR      -> MISS
close r=1     -> MISS
close r=2     -> MISS
close r=3     -> OK   https://m.qiekj.com/s?SN=NQT2024001&c=04
close r=4     -> OK   https://m.qiekj.com/s?SN=NQT2024001&c=04
```

安卓端 `tools/DotRoundTest.java` 直接跑生产代码 `ScanCore`：
`ub_dot_g1.png` → `(72ms)` 解出、`ub_dot_g2.png` → `(74ms)` 解出；
原来的 `tools/ScanCoreTest.java` 六组用例全部仍然通过，普通方块码无回归。

### 上一版的修复仍然有效

v1.0.4 修的三件事都还在：`takePicture()` 线程错位、预览尺寸回读、拍完照重新交缓冲；
网页端变焦按 `getCapabilities().zoom.min` 归一；结算改看 `order/detail` 的订单状态
（`0 待支付 / 1 已失效 / 2 使用中或已完成 / 3 已完成 / 4 退款中 / 5 已退款`，只有 2 和 3 算已结清），
不再因为 `order/sync` 落空就误报「支付还没确认」。
